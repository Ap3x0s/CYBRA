# Доставка и развёртывание

> English version: [docs/DEPLOYMENT.md](../DEPLOYMENT.md).

CYBRA поставляется **двумя сервисами** — backend с API и frontend на
nginx, который раздаёт SPA и проксирует `/api`. Десктопной сборки нет,
отдельного reverse proxy тоже: его роль играет nginx. Почему граница
проведена именно там — см. [ARCHITECTURE.md](ARCHITECTURE.md).

## Что поставляется

Два образа контейнера:

| Образ | Содержимое | Порт |
|---|---|---|
| `cybra-backend` | Python 3.12, FastAPI-приложение, супервизор прогонов | 8000 (внутренний) |
| `cybra-frontend` | nginx, собранная SPA, прокси на `/api` | 8080 (публикуется) |

Порт публикует только фронтенд. Бэкенд доступен исключительно через его
прокси в сети compose — второго открытого порта нет, и обойти прокси
нельзя.

Оба образа собираются CI из одного коммита и указываются по digest в
`infra/releases/*.yml`.

### Чего в образе нет

Стоит сказать прямо: это самый частый источник путаницы.

| Нет в образе | Откуда берётся |
|---|---|
| **Keycloak, LDAP** | Провайдер идентичности заказчика. Связь — четыре переменные `CYBRA_OIDC_*`, и ничего больше |
| PostgreSQL | Отдельный сервис: `--profile db` или база заказчика |
| garak, PyRIT, AgentDojo, promptfoo | `cybra setup` внутри работающего контейнера: они тянут torch и Node-бинарь |

`grep -i keycloak docker/Dockerfile` не находит ничего: провайдер не
запекается в образ и не будет. Один и тот же `cybra-backend:latest`
обслуживает и стенд с SSO, и стенд без него — разница только в окружении.

База данных в образ **не входит**: это отдельный сервис.

### База данных

Приложение ходит в PostgreSQL через `CYBRA_DATABASE_URL`:

```
CYBRA_DATABASE_URL=postgresql+psycopg://cybra:secret@db:5432/cybra
```

Отдельный сервис выбран сознательно: база переживает замену контейнера и
бэкапится по своему расписанию, а не вместе с образом.

Драйвер `psycopg[binary]` входит в образ, поэтому доустанавливать ничего не
нужно и компилятор с `libpq-dev` не требуются.

В `infra/compose.yaml` сервис PostgreSQL лежит под профилем `db` и по
умолчанию не поднимается: первый запуск не должен требовать второго сервиса.

```bash
# без базы: приложение на SQLite в томе
cd infra && docker compose --env-file .env -f compose.yaml up -d

# PostgreSQL: CYBRA_DATABASE_URL указывает на сервис `db`
printf 'CYBRA_DATABASE_URL=postgresql+psycopg://cybra:...@db:5432/cybra\nPOSTGRES_PASSWORD=...\n' >> infra/.env
cd infra && docker compose --env-file .env -f compose.yaml --profile db up -d
```

Все переменные перечислены в [`docker/.env.example`](../../docker/.env.example).

Если `CYBRA_DATABASE_URL` не задана, приложение работает на SQLite в
`/data/cybra.sqlite3`. Этот режим нужен для локального запуска без Docker и
для тестов, где поднимать сервер БД на каждый прогон несоразмерно. Для
промышленного стенда он не рекомендуется: всё состояние оказывается в одном
файле, который уходит вместе с контейнером.

Перенос существующей установки с SQLite на PostgreSQL:

```
python scripts/migrate_to_postgres.py /path/to/cybra.sqlite3
python scripts/verify_migration.py /path/to/cybra.sqlite3
```

Переносятся все строки вместе с id, после чего последовательности сдвигаются
за максимальный id: иначе первая же вставка через API упала бы на дубликате
ключа. Проверочный скрипт сверяет обе базы построчно и сравнивает не только
количество, но и содержимое — хеши паролей, JSON-поля и даты.

В образе **нет** `garak`, `PyRIT`, `AgentDojo`, `Promptfoo` и `HarmBench`: они
тянут torch или Node-бинарь на гигабайты. Консоль определяет, что доступно, и
честно показывает статус вместо падения в середине прогона. При необходимости
их ставят внутри работающего контейнера командой `cybra setup --tools …`.

Эта команда качает с PyPI, npm и GitHub. На стенде без интернета она работать
не может: пакеты нужно привезти с собой. См. [OFFLINE.md](OFFLINE.md) — сборка
и установка из bundle.

## Как производится артефакт

Родительский пайплайн — диспетчер; 18 этапов живут в трёх дочерних
пайплайнах, по одному на сервис:

```
запрос на слияние
   │
   ├── repo:precommit      хук на месте, аудит i18n                  (шаг 0)
   ├── repo:secrets        gitleaks, один раз на репозиторий         (шаг 6)
   ├── repo:iac            Dockerfile + compose + все пайплайны      (шаг 7)
   │
   ├── backend  → .gitlab/ci/pipelines/backend.yml
   │     validate, format, lint, test, sast, secrets, iac, build, sbom,
   │     sca, image-scan, deploy-test, dast, sign, release, approve,
   │     deploy-prod, smoke-prod, rollback
   │
   ├── frontend → .gitlab/ci/pipelines/frontend.yml
   │     те же 18 шагов, другие команды: npm ci вместо pip,
   │     nginx.conf вместо ruff, smoke проверяет прокси /api
   │
   └── infra    → .gitlab/ci/pipelines/infra.yml
         compose config, ansible --syntax-check, схема манифеста релиза
```

`rules: changes` решает, какие дочерние пайплайны запускать: правка в
`frontend/**` не запускает pytest вовсе.

### Когда пайплайн создаётся

Площадки ведут себя по-разному, и это стоит знать до того, как возникнет
вопрос «почему push ничего не запустил».

| Событие | GitLab | GitHub |
|---|---|---|
| Merge request / pull request | **да** — основной путь | да, по фильтру `paths:` |
| Тег `v*` | да — релизные стадии | да |
| Расписание | да — еженедельный обход CVE | да |
| Ручной / API | да | `workflow_dispatch` |
| **Прямой push в `main`** | **нет** — `when: never` | **да**, по фильтру `paths:` |
| Push в другие ветки | да | нужен подходящий `paths:` |

Правило `when: never` на push в `main` — не забывчивость: без него
пайплайн запускался на прямой push, то есть обходил ревью. Теперь в
`main` можно попасть только через merge request. Следствие стоит
называть прямо: после пуша в `main` пайплайн в GitLab надо запускать
руками (`POST /projects/:id/pipeline`), иначе площадки расходятся.

На GitHub то же разделение сделано фильтром `paths:`. `backend.yml`
перечисляет `backend/**`, `scan/**`, `security_suite/**`, `tests/**`,
`datasets/**`, `vendor/**`, `run.py`, `sources.lock.json`,
`docker/Dockerfile`; `frontend.yml` — `frontend/**`. Коммит, который не
трогает ни того, ни другого, не запускает ни одного workflow.

По git-тегу добавляется стадия release: `release:artifacts` — подпись cosign
в режиме keyless над digest образа и над SBOM, — и `release:publish`, который
переносит `:<sha>` в `:<tag>`.

Определено в [`.gitlab-ci.yml`](../../.gitlab-ci.yml) и трёх файлах в
[`.gitlab/ci/pipelines/`](../../.gitlab/ci/pipelines/). GitHub Actions
выполняет те же стадии двумя workflow, `backend.yml` и `frontend.yml`, где
ту же роль играют фильтры `paths:`. Отличается registry (ghcr.io там,
реестр GitLab здесь). Публикация из обоих мест в одно имя дала бы два
разных тега «latest», поэтому каждая площадка публикует в свой.

Из 18 этапов схемы DevSecOps реализованы 17 для каждого сервиса. Не
реализован один — DAST (этап 11): ему нужен живой стенд с подключённой
моделью, а поднимать модель в CI — гигабайты и часы. Он остаётся ручной
процедурой в [VALIDATION-CYBRA.md](VALIDATION-CYBRA.md). Пайплайн infra
реализует 15 из 18 — ему нечего собирать и подписывать, и файл говорит об
этом прямо, а не оставляет пробелы без объяснения.

### Подпись без ключа

`backend:sign` и `frontend:sign` подписывают в режиме keyless. Приватного
ключа нет нигде:
GitLab выпускает OIDC-токен (`id_tokens` с `aud: sigstore`), Sigstore меняет
его на короткоживущий сертификат, подпись попадает в журнал прозрачности.
Для этого проект должен жить на GitLab.com: на self-managed понадобится свой
Sigstore.

Подписывается digest, а не тег. Тег можно переставить на другой образ,
digest — нельзя. SBOM подписывается тоже, иначе перечень компонентов можно
подменить, не трогая подписанный образ.

Проверено на теге v0.2.3: обе подписи дошли до журнала прозрачности
(`tlog entry created with index: 4027397135`), а `cosign verify` сообщил
`The cosign claims were validated`.

До этого потребовались четыре прогона по тегам, каждый вскрывал одну
недостающую деталь. Записано, потому что каждая — ловушка:

| Прогон | Падение | Причина |
|---|---|---|
| v0.2.0 | `sha256sum: SHA256SUMS: No such file` | В alpine нет `python3`, а строка скрипта прятала это за `\|\| echo` |
| v0.2.1 | `digest неизвестен` | `image-digest.txt` не переходил границу стадии; нужен явный `artifacts: true` |
| v0.2.2 | `Cannot connect to the Docker daemon` | `docker-cli` даёт команду, но не демон — а демона в этом job'е быть не должно |
| v0.2.3 | успех | cosign ставится бинарником, а не запускается контейнером |

Общий шаблон у первых трёх: проверка, которая при сбое сообщает «всё
хорошо». `|| echo` подменяет настоящий сбой сообщением, пустой digest
передаётся дальше как значение. Теперь в обоих местах `exit 1`.

Детали, на которых легко потерять время:

- **Сборка идёт kaniko, а не `docker build`.** Канонический рецепт GitLab
  (`docker:dind` сервисом) требует привилегированного раннера, а на
  shared-раннере его нет. kaniko собирает в userspace: ни демона, ни
  привилегий. Образ — `ghcr.io/osscontainertools/kaniko`, поддерживаемый форк:
  Google заархивировал `GoogleContainerTools/kaniko` в июне 2025. Версия
  зафиксирована: `latest` у сборщика означает, что пайплайн краснеет сам по
  себе, без единой правки в репозитории.
- **Кеш слоёв живёт в registry** (`--cache-repo`): между job'ами нет демона,
  который мог бы его хранить. Второй прогон переиспользует все восемь слоёв.
- **kaniko не понимает `**/__pycache__` глубже второго уровня.** Docker
  понимает. Без дополнительных правил `**/__pycache__/**` и `**/*.pyc` в
  образ уезжает байткод локального интерпретатора разработчика — проверено
  на реальной сборке.
- Сканеры образа читают его **из registry**, поэтому им нужен `needs` на
  сборку. Без него тега ещё нет, trivy падает с `MANIFEST_UNKNOWN`, а ошибка
  прячется за `allow_failure`.
- `deploy:test` стягивает образ обратно и запускает его. Сборка, которая
  компилируется, но не стартует, падает здесь, а не в продакшене.

## Развёртывание

Разворачивает Ansible из `infra/`, управляясь манифестом релиза. Манифест
фиксирует каждый образ **по digest**, поэтому на хосте оказывается ровно
то, что собрал CI:

```bash
# 1. Одноразовый секрет. Потеря делает сохранённые ключи эндпоинтов нерасшифровываемыми.
python -c "import base64,os;print(base64.urlsafe_b64encode(os.urandom(32)).decode())"

# 2. Развернуть релиз в окружение
ansible-playbook -i infra/inventories/dev/hosts.yml \
  infra/ansible/playbooks/deploy.yml \
  -e release_id=cybra-0.1.0 \
  -e target_env=dev \
  -e backend_image=registry.gitlab.com/ap3x0/cybra/backend@sha256:<digest> \
  -e frontend_image=registry.gitlab.com/ap3x0/cybra/frontend@sha256:<digest>
```

Playbook проверяет входы, рендерит `.env` из `infra/configurations/`,
выполняет `docker compose config`, тянет образы, поднимает состав и ждёт
health. Отсутствующий секрет или битый digest останавливают его до того,
как что-либо скачано.

`CYBRA_COOKIE_SECURE=1` обязателен за HTTPS. Без него сессионная cookie
уходит открытым текстом — `infra/configurations/environments/prod-lab.yml`
его задаёт, dev и stage нет.

Вручную, без Ansible, для быстрой локальной проверки:

```bash
cd infra
printf 'BACKEND_IMAGE=%s\nFRONTEND_IMAGE=%s\nFRONTEND_PORT=8080\n' \
  "<backend@sha256:...>" "<frontend@sha256:...>" > .env
printf 'CYBRA_SECRET_KEY=%s\n' "<ключ>" > backend.env
printf 'FRONTEND_PORT=8080\n' > frontend.env
docker compose --env-file .env -f compose.yaml up -d
```

В `infra/compose.yaml` намеренно нет секции `build:`. Он тянет. С `build:`
compose молча собирает образ из локального контекста и перезаписывает тот же
тег, поэтому на двух машинах оказываются две разные сборки под одним именем —
ровно то, чего общая контейнерная развёртка не должна допускать. Собирает и
публикует только CI.

`docker/compose.prod.yaml` из эпохи монолита оставлен только помеченной
заглушкой: он развернул бы бэкенд без фронтенда — стенд, где API отвечает,
а открыть нечего.

`pull_policy` по умолчанию `always` по той же причине: если образа нет
локально, compose иначе попытается собрать его из контекста и упадёт с
невнятной ошибкой. Переопределяется через `CYBRA_PULL_POLICY`, чтобы
локальный стенд из `docker build` можно было проверить до публикации в
registry.

Открыть `http://<host>:8080`. При первом старте пароль администратора
печатается в журнал один раз; смените его в «Настройках».

### Окружение

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `CYBRA_SECRET_KEY` | генерируется в каталог данных | Ключ Fernet для API-ключей эндпоинтов. В продакшене задавать явно. |
| `CYBRA_DATA_DIR` | `/data` в образе, `var/` из исходников | База, артефакты прогонов, запасной ключ |
| `CYBRA_HOST` / `CYBRA_PORT` | `127.0.0.1` / `8000` | Адрес прослушивания |
| `CYBRA_ENGINE` | `subprocess` | `mock` запускает офлайн-фикстуру |
| `CYBRA_COOKIE_SECURE` | `0` | `1` за HTTPS |
| `CYBRA_SESSION_TTL_HOURS` | `12` | Время жизни сессии |
| `CYBRA_ALLOW_REGISTRATION` | `0` | Самостоятельная регистрация |

### Состояние

Две разные вещи, и у них разное расписание бэкапа:

```
PostgreSQL          пользователи, эндпоинты, датасеты, прогоны, шаги, находки
                    (отдельный сервис: см. «База данных» выше)
```

```
CYBRA_DATA_DIR/
  runs/            каталог на прогон: манифест, прогресс, записи, отчёт
  secret.key       только если CYBRA_SECRET_KEY не задан
  cybra.sqlite3    ТОЛЬКО когда запущено без CYBRA_DATABASE_URL
```

Бэкапить нужно и то, и другое. База хранит состояние консоли, артефакты
прогонов — доказательства, на которые ссылаются отчёты; одно без другого
не воспроизводимо. Сам контейнер одноразовый.

Не копируйте `cybra.sqlite3` в расчёте на бэкап PostgreSQL-установки: в
этом режиме файла не существует вовсе, база живёт в своём сервисе.

## Обновление

Развернуть более новый манифест — тот же playbook, другой `release_id`:

```bash
ansible-playbook -i infra/inventories/dev/hosts.yml \
  infra/ansible/playbooks/deploy.yml \
  -e release_id=cybra-0.2.0 -e target_env=dev \
  -e backend_image=<...>@sha256:<digest> -e frontend_image=<...>@sha256:<digest>
```

Пересоздаются только изменившиеся контейнеры: `state: present` с compose v2
не трогает неизменённые сервисы, поэтому обновление одного не
перезапускает другой.

Откат — это развёртывание предыдущего манифеста: digest там уже записаны,
пересобирать нечего. В этом и смысл фиксации по digest, а не по тегу.

Схема базы создаётся при старте. Добавление nullable-колонки не требует
релиза: `create_all()` создаёт новые таблицы, а `db.py` идемпотентно
добавляет недостающие колонки (`_ADDED_COLUMNS`), поэтому существующая
установка подхватывает их при следующем старте без чистого `CYBRA_DATA_DIR`.
Изменение, которое переименовывает колонку или меняет её тип, выходит за
рамки этого правила и по-прежнему требует ручной миграции. В
[VALIDATION-CYBRA.md](VALIDATION-CYBRA.md) это записано как известное
ограничение, а не как гарантия.

## Что не собирается

**Десктопное приложение — решение «позже», а не «нет».** В проектном документе
`cybra.exe` (PyInstaller) значится вторым каналом доставки — для локального
использования. Он не реализован. Принятое решение: браузерный формат — текущая
поставка, exe — отдельный блок работы позже. Веб-консоль и так работает в
браузере на той же машине, поэтому exe добавляет удобство (двойной клик, без
терминала), а не возможности. Когда его будут делать, честный состав тот же,
что у образа: UI + API + чистые адаптеры, без тяжёлых бенчмарков.

**Офлайн-режим PWA.** `frontend/public/manifest.webmanifest` есть, поэтому
консоль устанавливается на домашний экран телефона или десктопа, но service
worker отсутствует: без сети приложение не загрузится. Манифест делает его
похожим на приложение, но офлайн-приложением не делает. Пока это осознанно:
сами бенчмарки ходят по сети к эндпоинту модели, так что офлайн-оболочка
открывалась бы на экраны, которые ничего не могут.
