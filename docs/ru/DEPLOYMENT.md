# Доставка и развёртывание

> English version: [docs/DEPLOYMENT.md](../DEPLOYMENT.md).

CYBRA — веб-консоль: один процесс раздаёт и SPA, и API. Десктопной сборки нет,
отдельного контейнера для фронтенда тоже. Здесь описано, что именно является
артефактом, как он производится и что запускать на целевой машине.

## Что поставляется

Один образ контейнера. Внутри:

| Слой | Содержимое |
|---|---|
| Python 3.12 | FastAPI-приложение, супервизор прогонов |
| Статика SPA | React-сборка, раздаётся тем же процессом из `backend/static` |
| Точка входа | `python -m cybra --host 0.0.0.0` |

База данных в образ **не входит**: это отдельный сервис.

## База данных

Приложение ходит в PostgreSQL через `CYBRA_DATABASE_URL`:

```
CYBRA_DATABASE_URL=postgresql+psycopg://cybra:secret@db:5432/cybra
```

Отдельный сервис выбран сознательно: база переживает замену контейнера и
бэкапится по своему расписанию, а не вместе с образом.

Драйвер `psycopg[binary]` входит в образ, поэтому доустанавливать ничего не
нужно и компилятор с `libpq-dev` не требуются.

В `docker/compose.prod.yaml` сервис PostgreSQL лежит под профилем `db` и по
умолчанию не поднимается: первый запуск не должен требовать второго сервиса.

```
# SQLite в томе, без второго сервиса
docker compose -f docker/compose.prod.yaml up -d

# PostgreSQL: CYBRA_DATABASE_URL указывает на сервис `db`
printf 'POSTGRES_PASSWORD=...\nCYBRA_DATABASE_URL=postgresql+psycopg://cybra:...@db:5432/cybra\n' >> docker/.env
docker compose -f docker/compose.prod.yaml --profile db up -d
```

Все переменные перечислены в [`docker/.env.example`](../../docker/.env.example).

Если `CYBRA_DATABASE_URL` не задана, приложение работает на SQLite в
`/data/cybra.sqlite3`. Этот режим нужен для локального запуска без Docker и
для тестов, где поднимать сервер БД на каждый прогон несоразмерно. Для
промышленного стенда он не рекомендуется: всё состояние оказывается в одном
файле, который уходит вместе с контейнером.

Перенос существующей установки с SQLite на PostgreSQL:

```
python scripts/migrate_to_postgres.py /path/to/cybra.sqlite3
python scripts/verify_migration.py /path/to/cybra.sqlite3
```

Переносятся все строки вместе с id, после чего последовательности сдвигаются
за максимальный id: иначе первая же вставка через API упала бы на дубликате
ключа. Проверочный скрипт сверяет обе базы построчно и сравнивает не только
количество, но и содержимое — хеши паролей, JSON-поля и даты.

В образе **нет** `garak`, `PyRIT`, `AgentDojo`, `Promptfoo` и `HarmBench`: они
тянут torch или Node-бинарь на гигабайты. Консоль определяет, что доступно, и
честно показывает статус вместо падения в середине прогона. При необходимости
их ставят внутри работающего контейнера командой `cybra setup --tools …`.

## Как производится артефакт

```
запрос на слияние
   │
   ├── validate:precommit  ruff check + audit_i18n + pytest -q
   ├── format:check        ruff format --check (только свой код)
   ├── lint:frontend       npm ci && npm run build
   ├── test:unit           pytest tests/ -q            (90 тестов, без API-ключа)
   ├── security:sast       ruff + bandit (только HIGH)
   ├── security:secrets    gitleaks
   ├── security:iac        Dockerfile, .dockerignore, оба пайплайна
   ├── build:image         kaniko → :<commit-sha> всегда, :latest — только из main/тега
   ├── build:sbom          syft читает образ из registry
   ├── security:sca        pip-audit и лицензии
   ├── security:image      trivy читает образ из registry
   └── deploy:test         pull :<sha>, запуск, ожидание /api/v1/health
```

По git-тегу добавляется стадия release: `release:artifacts` — подпись cosign
в режиме keyless над digest образа и над SBOM, — и `release:publish`, который
переносит `:<sha>` в `:<tag>`.

Определено в [`.gitlab-ci.yml`](../../.gitlab-ci.yml). GitHub Actions выполняет
те же стадии тем же сборщиком; отличается только registry (ghcr.io там, реестр
GitLab здесь). Публикация из обоих мест в одно имя дала бы два разных тега
«latest», поэтому каждая площадка публикует в свой.

Из 18 этапов схемы DevSecOps реализованы 17. Не реализован один — DAST
(этап 11): ему нужен живой стенд с подключённой моделью, а поднимать модель
в CI — гигабайты и часы. Он остаётся ручной процедурой в
[VALIDATION-CYBRA.md](VALIDATION-CYBRA.md).

### Подпись без ключа

`release:artifacts` подписывает в режиме keyless. Приватного ключа нет нигде:
GitLab выпускает OIDC-токен (`id_tokens` с `aud: sigstore`), Sigstore меняет
его на короткоживущий сертификат, подпись попадает в журнал прозрачности.
Для этого проект должен жить на GitLab.com: на self-managed понадобится свой
Sigstore.

Подписывается digest, а не тег. Тег можно переставить на другой образ,
digest — нельзя. SBOM подписывается тоже, иначе перечень компонентов можно
подменить, не трогая подписанный образ.

Проверено на теге v0.2.3: обе подписи дошли до журнала прозрачности
(`tlog entry created with index: 4027397135`), а `cosign verify` сообщил
`The cosign claims were validated`.

До этого потребовались четыре прогона по тегам, каждый вскрывал одну
недостающую деталь. Записано, потому что каждая — ловушка:

| Прогон | Падение | Причина |
|---|---|---|
| v0.2.0 | `sha256sum: SHA256SUMS: No such file` | В alpine нет `python3`, а строка скрипта прятала это за `\|\| echo` |
| v0.2.1 | `digest неизвестен` | `image-digest.txt` не переходил границу стадии; нужен явный `artifacts: true` |
| v0.2.2 | `Cannot connect to the Docker daemon` | `docker-cli` даёт команду, но не демон — а демона в этом job'е быть не должно |
| v0.2.3 | успех | cosign ставится бинарником, а не запускается контейнером |

Общий шаблон у первых трёх: проверка, которая при сбое сообщает «всё
хорошо». `|| echo` подменяет настоящий сбой сообщением, пустой digest
передаётся дальше как значение. Теперь в обоих местах `exit 1`.

Детали, на которых легко потерять время:

- **Сборка идёт kaniko, а не `docker build`.** Канонический рецепт GitLab
  (`docker:dind` сервисом) требует привилегированного раннера, а на
  shared-раннере его нет. kaniko собирает в userspace: ни демона, ни
  привилегий. Образ — `ghcr.io/osscontainertools/kaniko`, поддерживаемый форк:
  Google заархивировал `GoogleContainerTools/kaniko` в июне 2025. Версия
  зафиксирована: `latest` у сборщика означает, что пайплайн краснеет сам по
  себе, без единой правки в репозитории.
- **Кеш слоёв живёт в registry** (`--cache-repo`): между job'ами нет демона,
  который мог бы его хранить. Второй прогон переиспользует все восемь слоёв.
- **kaniko не понимает `**/__pycache__` глубже второго уровня.** Docker
  понимает. Без дополнительных правил `**/__pycache__/**` и `**/*.pyc` в
  образ уезжает байткод локального интерпретатора разработчика — проверено
  на реальной сборке.
- Сканеры образа читают его **из registry**, поэтому им нужен `needs` на
  сборку. Без него тега ещё нет, trivy падает с `MANIFEST_UNKNOWN`, а ошибка
  прячется за `allow_failure`.
- `deploy:test` стягивает образ обратно и запускает его. Сборка, которая
  компилируется, но не стартует, падает здесь, а не в продакшене.

## Развёртывание

```bash
# 1. Одноразовый секрет. Потеря делает сохранённые ключи эндпоинтов нерасшифровываемыми.
python -c "import base64,os;print(base64.urlsafe_b64encode(os.urandom(32)).decode())"

# 2. Стянуть и запустить
docker pull ap3x0/cybra:latest

docker run -d --name cybra \
  -p 8000:8000 \
  -v cybra-data:/data \
  -e CYBRA_SECRET_KEY="<ключ из шага 1>" \
  -e CYBRA_COOKIE_SECURE=1 \
  ap3x0/cybra:latest
```

`CYBRA_COOKIE_SECURE=1` обязателен за HTTPS. Без него сессионная cookie
уходит открытым текстом.

Или через compose — там же задана политика рестарта:

```bash
printf 'CYBRA_SECRET_KEY=%s\n' "<ключ>" > docker/.env
docker compose -f docker/compose.prod.yaml pull
docker compose -f docker/compose.prod.yaml up -d
```

В `compose.prod.yaml` намеренно нет секции `build:`. Он тянет. С `build:`
compose молча собирает образ из локального контекста и перезаписывает тот же
тег, поэтому на двух машинах оказываются две разные сборки под одним именем —
ровно то, чего общая контейнерная развёртка не должна допускать. Собирает и
публикует только CI.

Указать конкретный registry можно через `CYBRA_IMAGE`:

```bash
CYBRA_IMAGE=ap3x0/cybra:latest \
  docker compose -f docker/compose.prod.yaml up -d
```

`pull_policy: always` задан по той же причине: если образа нет локально,
compose иначе попытается собрать его из контекста и упадёт с невнятной ошибкой.

Открыть `http://<host>:8000`. При первом старте пароль администратора
печатается в журнал один раз; смените его в «Настройках».

### Окружение

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `CYBRA_SECRET_KEY` | генерируется в каталог данных | Ключ Fernet для API-ключей эндпоинтов. В продакшене задавать явно. |
| `CYBRA_DATA_DIR` | `/data` в образе, `var/` из исходников | База, артефакты прогонов, запасной ключ |
| `CYBRA_HOST` / `CYBRA_PORT` | `127.0.0.1` / `8000` | Адрес прослушивания |
| `CYBRA_ENGINE` | `subprocess` | `mock` запускает офлайн-фикстуру |
| `CYBRA_COOKIE_SECURE` | `0` | `1` за HTTPS |
| `CYBRA_SESSION_TTL_HOURS` | `12` | Время жизни сессии |
| `CYBRA_ALLOW_REGISTRATION` | `0` | Самостоятельная регистрация |

### Состояние

Всё лежит в `CYBRA_DATA_DIR`:

```
cybra.sqlite3    база (WAL)
runs/            каталог на прогон: манифест, прогресс, записи, отчёт
secret.key       только если CYBRA_SECRET_KEY не задан
```

Этот каталог и нужно бэкапить. База и артефакты прогонов — единственное
состояние; сам контейнер одноразовый.

## Обновление

```bash
docker pull ap3x0/cybra:latest
docker compose -f docker/compose.prod.yaml up -d
```

Схема базы создаётся при старте, миграций пока нет: релиз, который её меняет,
требует чистого `CYBRA_DATA_DIR` или ручной миграции. В
[VALIDATION-CYBRA.md](VALIDATION-CYBRA.md) это записано как известное
ограничение, а не как гарантия.

## Что не собирается

**Десктопное приложение — решение «позже», а не «нет».** В проектном документе
`cybra.exe` (PyInstaller) значится вторым каналом доставки — для локального
использования. Он не реализован. Принятое решение: браузерный формат — текущая
поставка, exe — отдельный блок работы позже. Веб-консоль и так работает в
браузере на той же машине, поэтому exe добавляет удобство (двойной клик, без
терминала), а не возможности. Когда его будут делать, честный состав тот же,
что у образа: UI + API + чистые адаптеры, без тяжёлых бенчмарков.

**Офлайн-режим PWA.** `frontend/public/manifest.webmanifest` есть, поэтому
консоль устанавливается на домашний экран телефона или десктопа, но service
worker отсутствует: без сети приложение не загрузится. Манифест делает его
похожим на приложение, но офлайн-приложением не делает. Пока это осознанно:
сами бенчмарки ходят по сети к эндпоинту модели, так что офлайн-оболочка
открывалась бы на экраны, которые ничего не могут.
