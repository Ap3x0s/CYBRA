# Архитектура: два микросервиса

CYBRA работает как два сервиса вместо одного образа. Эта страница
объясняет, чем владеет каждый, где проходит граница и почему именно там.

## Зачем разделили

Первая версия поставлялась одним образом: Node собирал SPA, результат
копировался в Python-стадию, и fastapi раздавал и API, и статику. Для
монолита это было верное решение — один порт, нет CORS, нет второго
контейнера. Оно стало неверным, когда половины начали меняться с разной
скоростью.

Две конкретные цены одного образа:

| Проблема | Следствие |
|---|---|
| Любая правка `.jsx` меняла слой `COPY` в Python-образе | `pip install` fastapi и uvicorn перезапускался на каждой правке UI |
| Один пайплайн гонял все проверки для обоих стеков | правка CSS запускала `pytest` на 30 секунд; правка бэкенда пересобирала SPA |
| Один тег образа на два артефакта | бэкенд и фронтенд не могли версионироваться независимо |

## Два сервиса

| Сервис | Образ | Порт | Стек |
|---|---|---|---|
| `backend` | `cybra-backend` | 8000 | Python 3.12, FastAPI, uvicorn |
| `frontend` | `cybra-frontend` | 8080 | Node 22 (сборка) → nginx (раздача) |

```
             ┌────────────────────────────────┐
  браузер ──▶│  frontend — nginx :8080        │
             │    /        → /usr/share/nginx │
             │    /assets/ → долгий кеш       │
             │    /healthz → 200 ok (nginx)   │
             │    /api/*   → proxy_pass       │──┐
             └────────────────────────────────┘  │
                                                  ▼
                                 ┌──────────────────────────────┐
                                 │  backend — uvicorn :8000     │
                                 │    /api/v1/*                 │
                                 │    порт наружу не публикует  │
                                 └──────────────────────────────┘
```

Бэкенд **не публикует порт**. Единственный вход — фронтенд, который
проксирует `/api`. Нет второго открытого порта, который можно забыть
закрыть, и нет способа обойти прокси.

## Почему nginx проксирует, а не браузер ходит в бэкенд напрямую

`frontend/src/api.js` обращается к относительному пути `/api/v1`, то есть
браузер говорит с тем же origin, с которого загружена страница. Это одно
решение убирает три проблемы сразу:

- **Нет CORS.** Два origin потребовали бы `Access-Control-Allow-Origin`,
  обработку preflight и `credentials: include` в каждом запросе.
- **Работает cookie сессии.** Она `HttpOnly` на origin фронтенда.
  Кросс-доменный вызов не принёс бы её при политике `SameSite` по
  умолчанию, и пользователь молча оказался бы разлогинен.
- **Один публичный порт.** Бэкенд остаётся во внутренней сети compose.

## То, что выглядит деталью, но ею не является

**`resolver` и переменная в `proxy_pass`.** Очевидная форма —
`proxy_pass http://backend:8000;`. nginx разрешает это имя **однажды**,
при разборе конфигурации, и падает с
`host not found in upstream "backend"`, если бэкенда ещё нет. Последствия
два, и оба плохие: `nginx -t` нельзя выполнить при сборке образа (а
именно там ошибка в конфиге дешевле всего), и после перезапуска бэкенда с
новым IP nginx продолжает стучаться на старый и отдаёт 502 до
собственного рестарта. Поэтому в конфиге:

```nginx
resolver 127.0.0.11 valid=10s ipv6=off;
set $backend_upstream "backend:8000";
proxy_pass http://$backend_upstream;
```

**`pid` перенесён в `/tmp`.** nginx:alpine пишет `/run/nginx.pid` и
временные файлы в `/var/cache/nginx`, оба каталога принадлежат root. От
пользователя `nginx` демон умирает на старте с
`open() "/run/nginx.pid" failed (13: Permission denied)`. Снаружи это
выглядит как «healthcheck не отвечает», поэтому диагноз ищут не там.
`frontend/Dockerfile` переписывает путь, а `nginx -t` проверяет результат
при сборке.

**`try_files`.** Без него перезагрузка страницы на `/runs/123` отдаёт
404, хотя переход внутри приложения работает: маршрут существует только
в react-router, а не на диске.

## Структура репозитория

Задание допускало один репозиторий, поэтому границы сервисов
воспроизводятся каталогами и пайплайнами, а не отдельными проектами
GitLab:

| Репозиторий роадмапа | Здесь | Чем держится граница |
|---|---|---|
| `ci-templates` | `.gitlab/ci/templates/` | `include:` + `extends:` |
| `docker-images` | не выделяем | официальные `python:3.12-slim` / `node:22-alpine` покрывают задачу |
| `applications/infra` | `infra/` | compose, Ansible, inventories, releases |
| `configurations` | `infra/configurations/` | Jinja2-шаблоны `.env.j2` |
| `microservices/backend` | `backend/`, `scan/`, `security_suite/` | дочерний пайплайн `backend` |
| `microservices/frontend` | `frontend/` | дочерний пайплайн `frontend` |

`scripts/check_repo_structure.py` следит за границей: падает, если в
бэкенде появится JS-исходник, если `docker/Dockerfile` начнёт собирать
Node-стадию или если `frontend/nginx.conf` потеряет прокси `/api`.

## Два пайплайна

Родительский `.gitlab-ci.yml` — диспетчер. Он решает, **какой** пайплайн
запустить, и выполняет проверки, общие для обоих сервисов. 18 этапов
схемы DevSecOps живут в дочерних файлах:

```
.gitlab-ci.yml
├── repo:precommit        проверка хука, одна на репозиторий
├── repo:secrets          gitleaks, один раз
├── repo:iac              Dockerfile + compose + все пайплайны
│
├── backend   → .gitlab/ci/pipelines/backend.yml    (18 шагов)
├── frontend  → .gitlab/ci/pipelines/frontend.yml   (18 шагов)
└── infra     → .gitlab/ci/pipelines/infra.yml      (CD: 15 из 18)
```

`rules: changes` — то, что делает разделение настоящим: правка в
`frontend/**` не запускает pytest вовсе.

На GitHub то же разделение — два workflow, `backend.yml` и
`frontend.yml`, где ту же роль играют фильтры `paths:`.

### Чем пайплайны отличаются

Схема общая, наполнение — нет.

| Шаг | backend | frontend |
|---|---|---|
| 2 Format | `ruff format --check` | конфиг Vite разбирается, сборка проходит |
| 3 Lint | `ruff check` | сборка разрешает все импорты |
| 4 Tests | `pytest --junitxml` | структура production-сборки + JUnit |
| 5 SAST | ruff-B + bandit (HIGH) | `npm audit --audit-level=high` |
| 7 IaC | Dockerfile, compose | **nginx.conf**: директивы, баланс скобок |
| 9 SCA | pip-audit + лицензии | license-checker, проверка GPL |
| 12 Smoke | health + 401 без сессии | SPA **+ /api через nginx** + fallback |

Smoke фронтенда важнее остальных: он поднимает оба сервиса и запрашивает
`/api/v1/health` **через nginx**. Забытый `proxy_pass` ловится там, а не
на стенде заказчика.

## Инфра

```
infra/
├── compose.yaml                  оба сервиса + профиль postgres
├── ansible/
│   ├── playbooks/deploy.yml      валидация → render → pull → up → health
│   └── roles/
│       ├── preflight/            docker, compose-плагин, каталоги, секреты
│       └── deploy_compose/       render .env, compose config, pull, up, проверка
├── inventories/{dev,stage,prod-lab}/hosts.yml
├── configurations/
│   ├── templates/*.env.j2        Jinja2, рендерится при деплое
│   └── environments/*.yml        несекретные параметры по окружениям
└── releases/cybra-0.1.0.yml      манифест: digest каждого сервиса
```

Манифест — центр модели. Он фиксирует каждый сервис **по digest**, а не
по тегу, поэтому «что развёрнуто» имеет ровно один ответ. Один и тот же
digest едет из dev в stage и prod-lab без пересборки.

`scripts/update_release.py` подставляет digest из вывода kaniko;
`scripts/check_release.py` не пропускает манифест с заглушкой.

## Что не покрыто

| Пункт | Почему |
|---|---|
| Kubernetes | Роадмап прямо говорит: в этот маршрут не входит |
| Ansible против реального хоста | Целевого хоста нет; playbook проверяется syntax-check в CI и локально |
| Vault | Секреты из CI-переменных; Vault — ветка «Укрепление CD-хоста» |
| DAST (этап 11) | Нужен живой стенд с моделью — гигабайты и часы в CI |
| Миграции БД | Отдельная ветка роадмапа, после проверки отката контейнеров |
