# CYBRA — дизайн продукта

Статус: утверждён 09.11.2026. Реализация ведётся по `docs/plan.md`.

## Задача

Дать «прикладному админу» (ИБ-специалисту, который не лезет в код) инструмент, который
прогоняет современные бенчмарки безопасности LLM по произвольной OpenAI-совместимой модели,
хранит историю и показывает стандартизированные метрики с расшифровкой.

Готовый движок уже есть в `run.py` + `security_suite/`: восемь адаптеров, relay с бюджетом
запросов, API-судья, датасеты, консолидированный отчёт. Продукт — всё, что вокруг него:
веб-UI, база отчётов, версионирование датасетов, авторизация, графики.

### Что болит у пользователя сегодня

| Проблема | Следствие |
|---|---|
| Запуск только через CLI с десятком флагов | Не-разработчик не может начать |
| Отчёт — файл в каталоге | Нет истории, нельзя сравнить модели между прогонами |
| Датасет правится руками в JSONL | Нет версий, нельзя воспроизвести прогон, нельзя откатить |
| Нет авторизации | Нельзя отдать стенд нескольким людям |
| Метрики у каждого инструмента свои | Нельзя показать руководству одну таблицу |

## Решение

Веб-приложение из трёх слоёв в одном репозитории, с границами под будущее разделение по
репозиториям.

```
llm-security-app/
├── scan/         # движок: профили прогонов, изоляция инструментов, прогресс, отмена
├── backend/      # FastAPI: REST/SSE, SQLite, auth, отчёты, метрики
├── frontend/     # SPA: тёмная консоль + светлые печатные отчёты
├── security_suite/  # существующее ядро оценок (не трогаем)
├── datasets/     # данные бенчмарков
├── docker/       # один образ + compose.prod.yaml
└── docs/         # спека, ADR, словарь метрик, план
```

### Ключевое решение: scan/ — супервизор, а не переписывание

`scan/` не переписывает `security_suite/`. Он запускает существующий `run.py` в отдельном
процессе и читает его файловый контракт (`manifest.json`, `summary.json`, `records.jsonl`,
`http.jsonl`, `status.json`). Причины:

1. **Логика оценок не должна регрессировать.** Судья, критерии PASS/FAIL и relay уже
   проверены против реальных моделей. Переписывание в библиотеку даёт риск без выгоды.
2. **Изоляция.** garak и PyRIT тянут конфликтующие ML-зависимости. Процесс на инструмент
   изолирует их так, как это уже работает.
3. **Отменяемость.** Убить дерево процессов проще, чем заставить библиотеку вежливо
   остановиться посреди HTTP-запроса.

При этом вводится шов `EngineBackend` (`subprocess` | `inprocess` | `mock`), чтобы позже
подменить реализацию без правок API и UI.

### Поток данных прогона

1. UI создаёт `POST /runs` с профилем, списком целей (endpoint+model) и инструментов.
2. `scan/` материализует датасеты выбранной версии во временный каталог, пишет `job.json`.
3. Запускается `python run.py run ...` с параметрами из профиля.
4. Параллельный сторож читает `http.jsonl` и `worker.log`, публикует прогресс в SSE.
5. По завершении `summary.json` и `records.jsonl` импортируются в БД.
6. UI обновляет карточку прогона и графики.

### Модель данных (SQLite + WAL)

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `users` | Учётные записи | `email`, `password_hash` (argon2), `role` (admin/operator/viewer) |
| `sessions` | Веб-сессии | `token_hash`, `expires_at`, `user_id` |
| `endpoints` | API-серверы | `base_url`, `auth_type`, `secret_encrypted`, `verify_tls`, `ca_pem`, `default_headers` |
| `targets` | Модель на эндпоинте | `endpoint_id`, `model_id`, `temperature`, `token_param`, `drop_params`, `extra_body` |
| `dataset_versions` | Версии набора кейсов | `name`, `semver`, `sha256`, `origin`, `changelog`, `parent_id` |
| `dataset_cases` | Нормализованные кейсы | `version_id`, `case_id`, `category`, `prompt`, `metadata_json` |
| `runs` | Прогон | `profile`, `status`, `started_at`, `finished_at`, `config_json` |
| `run_targets` | Цель × прогон | `run_id`, `target_id`, `dataset_version_id` |
| `run_steps` | Модель × инструмент | `run_id`, `target_id`, `tool`, `completeness`, `counts_json`, `error` |
| `findings` | Нормализованные кейсы | `run_step_id`, `case_id`, `category`, `verdict`, `prompt`, `answer`, `reason` |

### Метрики

Словарь определён в `docs/metrics.md`; каждая метрика имеет `id`, формулировку, формулу и
ограничения. Это важно, потому что инструменты считают разное: у garak единица — решение
детектора, у остальных — отдельный кейс.

Базовый набор: `attack_success_rate`, `failed_check_rate`, `refusal_rate`,
`benign_utility_rate`, `injection_follow_rate`, `leak_rate`, `unscored_rate`, `coverage`.

Инвариант: **кросс-инструментный агрегированный ASR не показывается.** Вместо него —
матрица «модель × инструмент» и явный дисклеймер.

### API

`/api/v1`: `auth/*`, `endpoints`, `targets`, `datasets` (+`versions`, `cases`, импорт, diff),
`profiles`, `runs` (+`events` SSE, `cancel`), `reports` (`md`/`html`/`json`), `metrics`,
`capabilities`, `health`.

### UI

Тёмная консоль (SL UI Library как источник компонентов) для операций; светлая печатная
версия отчёта отдельным маршрутом. Экраны: Login, Dashboard, Runs (список + мастер
создания), Run detail с живым прогрессом, Reports, Datasets (редактор кейсов, импорт,
diff версий), Models/Endpoints, Metrics, Settings.

### Доставка

| Канал | Состав | Назначение |
|---|---|---|
| `cybra.exe` (PyInstaller) | UI + API + чистые адаптеры | open-source, локальный запуск |
| Docker-образ | Всё + garak/PyRIT/promptfoo | корпоративный стенд |

Проверка окружения на старте: `scan/capabilities.py` определяет, какие нативные инструменты
доступны, и отдаёт это в `GET /capabilities`. UI показывает карточку «не установлено» с
командой установки вместо падения.

## Безопасность

- Пароли — argon2; сессии — HttpOnly SameSite=Lax cookie, `Secure` при HTTPS.
- API-ключи эндпоинтов шифруются Fernet-ключом из `CYBRA_SECRET_KEY`; в БД и отчётах —
  только отпечатки.
- Отчёты могут содержать нежелательный контент: доступ к ним ограничен ролью и логируется.
- Первый запуск создаёт администратора и печатает одноразовый пароль в консоль.
- CSRF-защита для изменяющих запросов, rate limit на логин.

## Что не входит в первый релиз

SSO/LDAP, multi-tenant, расписание прогонов по cron, интеграции со Slack, мобильная версия,
полный набор всех существующих атак benchmark'ов. Всё это — последующие версии (см. бэклог).

## Критерии готовности MVP

1. Админ входит в UI, заводит endpoint и две модели.
2. Выбирает инструменты и версию датасета, запускает прогон, видит прогресс без перезагрузки.
3. Прогон против mock-сервера завершается, отчёт открывается и экспортируется.
4. Датасет правится в UI, получает новую версию, старый прогон ссылается на прежнюю.
5. Дашборд показывает сравнение двух моделей по метрикам с расшифровкой.
6. `docker run` поднимает всё одной командой.
