# Вход через OpenID Connect (корпоративный SSO)

Приложение умеет пускать людей двумя способами: локальным паролем и
корпоративным аккаунтом через Keycloak. Второй способ описан здесь.

## Термины в одном абзаце

**LDAP** — каталог, где лежат сотрудники и их пароли (обычно Active
Directory). **Keycloak** — сервер, который читает LDAP и выдаёт приложениям
подтверждение «этот человек настоящий». **OIDC** — протокол, по которому
приложение разговаривает с Keycloak. **SSO** — результат: вошёл один раз,
дальше все приложения открываются без пароля.

Пароль сотрудника идёт с Keycloak на Keycloak. Приложение его **не видит
вообще** — это главная выгода схемы.

## Что происходит при входе

```
1. Браузер  →  /api/v1/auth/oidc/login
2. Приложение → редирект в Keycloak (state, nonce, PKCE)
3. Человек вводит пароль НА СТРАНИЦЕ Keycloak
4. Keycloak проверяет пароль в LDAP
5. Keycloak → /api/v1/auth/oidc/callback?code=...&state=...
6. Приложение меняет code на токены (server-to-server, с client_secret)
7. Приложение проверяет id_token: подпись, iss, aud, exp, nonce
8. Приложение создаёт СВОЮ сессию — ту же, что при входе по паролю
```

Шаг 8 — ключевой: `create_session()` не знает, как человек вошёл. Дальше
всё работает как раньше: cookie, CSRF, роли.

## Настройка

Переменные окружения (см. `infra/keycloak/env.oidc.example`):

| Переменная | Что это |
|---|---|
| `CYBRA_OIDC_ISSUER` | адрес realm, например `https://keycloak.company.ru/realms/corp` |
| `CYBRA_OIDC_CLIENT_ID` | идентификатор клиента в Keycloak |
| `CYBRA_OIDC_CLIENT_SECRET` | секрет клиента. **Только на сервере** |
| `CYBRA_OIDC_REDIRECT_URI` | полный внешний адрес callback |
| `CYBRA_OIDC_DEFAULT_ROLE` | роль при первом входе (по умолчанию `viewer`) |
| `CYBRA_OIDC_ALLOW_LOCAL` | `1` — локальный пароль работает, `0` — только SSO |

OIDC включается, когда заданы первые четыре. Если хоть одна пуста — режим
выключен, кнопка в интерфейсе не рисуется, эндпоинты отвечают 404.

### Со стороны Keycloak

1. Realm создан, клиент типа **confidential** (не public: у него есть
   секрет, и он живёт на сервере).
2. `Valid redirect URIs` — ровно тот адрес, что в `CYBRA_OIDC_REDIRECT_URI`.
   Расхождение в одном символе даёт отказ на этапе редиректа.
3. `Client authentication` включена, `Standard flow` включён,
   `Direct access grants` выключен (пароль должен вводиться на странице
   провайдера, а не через API).
4. LDAP-федерация настроена, если сотрудники должны приходить из каталога.

## Что проверяется в токене и почему

Это не «хорошие практики», а то, без чего получится дыра:

| Проверка | Что было бы без неё |
|---|---|
| Подпись по JWKS | токен можно нарисовать в блокноте |
| `alg != none` | токен без подписи считался бы валидным |
| `iss` | токен выпущен подставным сервером |
| `aud` | токен выпущен для другого приложения и его подсунули нам |
| `exp`, `iat`, `nbf` | утёкший токен работает вечно |
| `nonce` | токен от другой попытки входа принимается повторно |
| `state` | CSRF на callback: подсунули чужой `code` |
| подпись cookie состояния | подменили nonce в cookie, и проверка стала бессмысленной |

Все эти проверки покрыты тестами в `tests/test_oidc.py` — каждый строит
настоящий RSA-ключ и настоящий JWT, а не мокает проверку.

## Роли: почему не из токена

В Keycloak тоже есть роли, и соблазн прочитать их из токена велик. **Не
надо.** Кто может выпустить токен для нашего клиента (или админ чужого
realm), получил бы админку в приложении.

Правильно так:

- Keycloak отвечает только на вопрос **«кто это»** — через `sub`;
- приложение само решает **«что ему можно»** — роль лежит в нашей БД;
- при первом входе выдаётся минимальная роль из `CYBRA_OIDC_DEFAULT_ROLE`;
- повышение — вручную через «Настройки».

Привязка идёт по `sub`, а не по email: email сотрудник может сменить, и
привязка по нему либо отнимет доступ, либо — хуже — отдаст чужой аккаунт
после переиспользования адреса.

## Локальный админ остаётся

Это аварийный вход. Если Keycloak лёг или его настройки сломаны, нужен
способ зайти и починить — иначе сломанный SSO блокирует починку SSO.

`CYBRA_OIDC_ALLOW_LOCAL=1` (по умолчанию) оставляет пароль работающим.
В корпоративном развёртывании ставится `0`: тогда учётка, пришедшая через
провайдера, по паролю не войдёт — у неё и пароля нет, хеш пустой.

## Тестовый стенд

`infra/keycloak/compose.yaml` поднимает Keycloak, LDAP и веб-интерфейс к
каталогу. Отдельный файл и отдельный каталог: это внешний провайдер, а не
часть поставки CYBRA.

```bash
cd infra/keycloak
docker compose up -d          # ~60 секунд на импорт realm

# Keycloak:      http://localhost:8080/admin   (admin / admin)
# LDAP-дерево:   http://localhost:8081         (cn=admin,dc=example,dc=org / admin)
```

Тестовые сотрудники приходят из LDAP (`infra/keycloak/ldap/staff.ldif`):

| Логин | Пароль | Кто |
|---|---|---|
| `ivanov` | `password` | Иван Иванов, инженер по безопасности |
| `petrova` | `password` | Анна Петрова, аналитик |

Плюс `demo` / `demo` — локальная учётка в самом Keycloak, для сравнения.

Затем приложение:

```bash
export CYBRA_OIDC_ISSUER=http://localhost:8080/realms/cybra
export CYBRA_OIDC_CLIENT_ID=cybra
export CYBRA_OIDC_CLIENT_SECRET=cybra-local-dev-secret-not-for-production
export CYBRA_OIDC_REDIRECT_URI=http://localhost:8011/api/v1/auth/oidc/callback
python -m cybra --port 8011
```

## Частые ошибки

**`host not found` или ошибка при обмене кода.** `redirect_uri` в
приложении и в клиенте Keycloak должны совпадать символ в символ, включая
`http` против `https` и `localhost` против `127.0.0.1`.

**`state не совпал`.** Браузер начал вход на одном хосте, а callback
пришёл на другой. Для cookie это разные домены. Держите один адрес — тот,
что в `CYBRA_OIDC_REDIRECT_URI`.

**`nonce не совпал`.** Токен от другой попытки входа. Обычно это открытые
две вкладки со входом одновременно; помогает повторить вход.

**`Issuer провайдера не совпал`.** За прокси Keycloak виден под другим
именем. Задайте `CYBRA_OIDC_ISSUER_OVERRIDE` — то, что написано в токене.

**Кнопка не появляется.** Не заданы все четыре обязательные переменные,
или фронтенд собран старым. Проверьте `/api/v1/auth/oidc/enabled`.

## Ограничения

- Поддерживается только authorization code flow. Implicit и password grant
  не поддерживаются намеренно: первый отдаёт токены в URL, второй означает,
  что пароль вводится в нашем интерфейсе.
- Алгоритмы подписи — RS256/384/512. ES256 и HMAC не поддерживаются: одна
  честная реализация лучше трёх половинчатых.
- Refresh-токены не используются: сессия живёт по нашим правилам
  (`CYBRA_SESSION_TTL_HOURS`), а не по времени жизни токена провайдера.
- Single Logout (выход из всех приложений сразу) не реализован: выход
  закрывает нашу сессию. Для полного SSO-выхода нужен back-channel logout,
  это отдельная работа.
